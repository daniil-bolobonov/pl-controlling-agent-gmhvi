# MCP translation file generator

Generate an MCP translation file from an API spec (OpenAPI or OData).

This skill produces exactly **two new files** per API spec: `translation.json` and `.tool-list.json`. The original API spec file is copied to the output folder, but it's not generated by this skill.
This skill orchestrates the process: resolves inputs, calls the tool (providing the API spec file path, API type, and ORD ID), then **prunes the tool set down to what the asset actually needs**.

### The two files and their relationship (read this first)

These two files look similar but have **opposite** roles. Understanding this is essential; several downstream skills depend on it:

- **`translation.json`** is the **live, authoritative set**. Its `tools[]` array contains **only the tools that are enabled** for this asset. This is the file that is deployed and used to generate the MCP server card, and it is the file an agent wires its tools from. A tool is "enabled" if and only if it is present in this array. There is **no `enabled`/`disabled` flag**; removing a tool from the array *is* disabling it.
- **`.tool-list.json`** is the **immutable full backup**. It is written **once, from the full generator output, before any pruning**, and lists **every** tool the API exposes. It is **never pruned**. Its only purpose is to let a user (or a later update) re-add a tool that pruning removed from `translation.json`. `.tool-list.json` is therefore a **superset** of `translation.json`'s tools.

Consequence: pruning (Phase 4) edits **`translation.json` only** and must **never** touch `.tool-list.json`.

**Hard invariant:** `translation.json` is authoritative and **MUST always exist** wherever `.tool-list.json` exists. A folder that has `.tool-list.json` but no `translation.json` is a **corrupted asset**, not a recoverable state. Downstream skills must **never** fall back to `.tool-list.json` for wiring or cataloguing when `translation.json` is absent; they must hard-stop and report the corruption. (`.tool-list.json` is the full un-pruned set, so falling back would silently wire every tool and defeat pruning.)

**Invocation context:** Typically invoked by the `specification` skill, not directly by users. If invoked manually, ensure all prerequisites are met (API specs in place, tasks referencing APIs).


## Terminology
These terms have precise meanings throughout this document:

- **STOP**: Halt execution of this skill entirely. Do not proceed to any subsequent step. Explain to the user what went wrong, what is missing, and how to fix it. If this skill was invoked by another agent or skill, return control to the caller with the error details.
- **Log/Decision log**: When you make a non-trivial choice (e.g. selecting an API type, skipping an endpoint, choosing a tool name), emit a short line in the chat: `[MCP-SKILL] <what> — <why>`. This improves debugging and reproducibility. Always include the prefix `[MCP-SKILL]` to distinguish these messages from others, even if it was not explicitly required.

## Tools
- **mcp_builder_generate_translation**: MCP tool that generates an MCP translation file from an API spec. Invoke it via the `jl` CLI — see Phase 3 Step 3.

## Prerequisites
- The file `specification/<asset-name>/specification.md` exists
- Atleast one task in `specification/<asset-name>/specification.md` references an API integration (e.g., contains phrases like "API", "integration", "OData", "REST", "service", or an ORD ID pattern like `sap.*:apiResource:*`).
- The directory `specification/<asset-name>/api-specs/` exists and contains at least one spec file.


## Workflow
If prerequisites aren't met, first check the 'Troubleshooting' section to fix them so workflow can be executed properly.

### Phase 1: Collect list of spec files, check for existing translation files.
#### List of spec files
- Identify the relevant API integration tasks from `specification/<asset-name>/specification.md`.
- You MUST record every spec file found in `specification/<asset-name>/api-specs/`. For each file, extract the ORD ID from the task description or from the filename/content. If there are multiple spec files, repeat this step for each one, producing one new file per API spec.
#### Existing Translation files
- Check for existing translation files. If **any file exists** → Ask the user: "Translation files already exist at `{paths-list}`. What would you like to do?"
  - **Re-validate** -> Record every spec file found in `specification/<asset-name>/api-specs/`. For each file, extract the ORD ID from the task description or from the filename/content. If validation fails, check Troubleshooting. **Do not re-prune and do not touch `.tool-list.json`**: re-validation verifies the existing files, it does not regenerate them, so any prior pruning in `translation.json` is preserved.
  - **Update (change which tools are enabled)** -> Keep both files; go straight to **Phase 4** to re-run pruning against the current scope. Treat `.tool-list.json` as the source of the full tool set: compute the new keep-set and write it to `translation.json`'s `tools[]`. This both re-adds tools (copy their objects from `.tool-list.json`) and removes tools, without regenerating. **Never regenerate or overwrite `.tool-list.json`** in this mode.
  - **Overwrite (regenerate from the API spec)** -> reinvoke the `specification` skill to rewrite all files and recreate the folder from scratch. **Warn the user first** that this discards any manual tool selection and starts over from the full API. (Mechanically, the backup is rebuilt from the generator output and `translation.json` is regenerated full before Phase 4 re-prunes it; keep that detail out of the user-facing warning.)
  - **Abort** -> STOP.


### Phase 2: Input Resolution

You now have recorded the list of spec files from `specification/<asset-name>/api-specs/`. Now resolve the remaining inputs for each spec file.


#### Read the API spec paths

Find each spec file path (from the `specification/<asset-name>/api-specs/` directory). These files will be used to generate the MCP translation.

#### Resolve the API type

Determine the API type for each spec file. Use this order:

1. **File extension**:
   - `.edmx` or `.xml` → `edmx`
   - `.json`, `.yaml`, `.yml` → inspect file content (see step 3)
2. **ORD ID suffix** — if the ORD ID ends with `:edmx` or `api-discovery-results.md` exists and target type is specified there, use that.
3. **Spec file content** — only OpenAPI v2/v3 and OData (EDMX) are supported. Check in order:
   - JSON or YAML where `x-sap-api-type` is present and its value is not `"REST"` → **STOP**. Do NOT write any files. Do NOT proceed to any subsequent phase. Do NOT attempt workarounds such as mock tools, simulated integrations, or adapters — these are not valid substitutes. Inform the user of the unsupported API type and return control to the caller with the error details.
   - JSON or YAML with `swagger: "2.0"` → `openapi-v2` ✓
   - JSON or YAML with `openapi: "3.*"` → `openapi-v3` ✓
   - XML whose root element is `<edmx:Edmx>` → `edmx` (OData) ✓
   - Any other format (e.g. WSDL, GraphQL schema) → **STOP**. Only OpenAPI v2/v3 and OData (EDMX) are supported. Do NOT enrich or patch the spec. Inform the user and return control to the caller.
   - Format cannot be determined → STOP and ask the user.

Log the decision: `API type: {type} — {reason}`.

#### Resolve the ORD ID

Extract the ORD ID for the source API. Search in this order:
- If **`api-discovery-results.md`** exists, 
  — Match the API spec filename to the **Local Spec Path** column. Extract the ORD ID from the matching row. This is the most reliable source since it was populated during API Discovery by the `specification` skill.
- The task description in the specification files (look for a pattern like `sap.*:apiResource:*`).
- Metadata or annotations inside the spec file itself.
- Ask the user (last resort): "What is the ORD ID of the source API? (e.g., `sap.s4:apiResource:dispute-service:v1`)"

- If **found** → Record the ORD ID. Proceed.
- If **not found** → Ask the user: "What is the ORD ID of the source API? (e.g., `sap.s4:apiResource:dispute-service:v1`)"
  - If the user cannot provide one → STOP.
  - If the user provides one → Record it. Proceed.

Log the decision: `ORD ID: {ordId} — {source}`.


### Phase 3: Generate Translation File

For each API spec file, generate the translation via the `jl` CLI (see Step 3).

#### Step 1 — Prepare the output folder

Derive `<api-spec-stem>` from the API spec filename (see details about this process in the reference section) and use it as the output folder name.

#### Step 2 — Store the original API spec file in the output folder

Copy the original API spec file from `specification/<asset-name>/api-specs/` into the output folder, renaming it to `api-spec.<extension>` (where `<extension>` is the original file extension, e.g., `json`, `edmx`, etc.). Write it to:

```
specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<extension>
```

#### Step 3 — Call the tool

Before invoking, log the resolved inputs:

```
[MCP-SKILL] API type: <api-type> — <reason>
[MCP-SKILL] ORD ID: <ord-id> — <source>
[MCP-SKILL] Spec file: <spec-file-path>
```

Generate the translation by invoking `mcp_builder_generate_translation` via the `jl` CLI:
```bash
jl mcp call ibd-mcp-server mcp_builder_generate_translation spec="$(cat specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<extension>)" apiType=<apiType> apiOrdId=<apiOrdId> > translation.json
```
Invoke it **only** this way — never as a direct MCP tool call. The `$(cat file)` expansion reads the spec from disk into the argument, and the output is redirected to `translation.json`, so neither the full API spec nor the generated file ever enters the LLM context window. Passing the spec as a direct tool argument would corrupt the context. Use `$(cat file)`, not `$(< file)` — the bash `$(< file)` shortcut expands to an empty string in the non-interactive shell `jl` runs, so the spec would arrive empty and the tool would error.

On success the output is a flat `MCPTranslation` JSON object (`mcpTranslationVersion`, `tools`, etc. at root level). The tool guarantees the translation has passed validation before returning it.

**After running the command, always check for errors before proceeding:**

1. If the command did not exit successfully, or `translation.json` is missing/invalid JSON → see error handling below.
2. Check whether the tool itself reported an error (exit code 0 does **not** guarantee success — `jl` exits 0 even when the MCP tool returns `isError: true`):
   ```bash
   jq -e '.isError == true' translation.json
   ```
   If this returns true, extract the error message:
   ```bash
   jq -r '.content[0].text' translation.json
   ```
   Then delete `translation.json` (it contains an error, not a translation) and handle the error as described below.

**Error handling:**
- If the error message includes a `toolNameOverrides` hint (e.g. `Re-call with toolNameOverrides: { "long_name": "<shortName>" }`):
  1. Show the hint to the user and ask them to provide a shorter name (max 64 chars) for each listed tool.
  2. Re-call with the overrides:
     ```bash
     jl mcp call ibd-mcp-server mcp_builder_generate_translation \
       spec="$(cat specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<extension>)" \
       apiType=<apiType> apiOrdId=<apiOrdId> \
       toolNameOverrides='{"current_long_name":"short_name"}' > translation.json
     ```
  3. Repeat the error check after each re-call until the call succeeds or the user chooses to abort.
- For any other error → STOP and report the error details to the user.


After the tool completes, validate the translation file to confirm it conforms to the MCP translation schema:

```bash
jl mcp call ibd-mcp-server mcp_builder_validate_translation \
  translation="$(cat translation.json)" > validation-result.json
jq -e '.isError == true' validation-result.json
```

If validation returns `isError: true`, extract the error:

```bash
jq -r '.content[0].text' validation-result.json
```

→ STOP and report the validation error. Do not proceed with an invalid translation file. Delete `validation-result.json` before continuing.

Once generation and validation have both succeeded, write both files (`translation.json` and `.tool-list.json`) to the output folder:

1. Move/copy the generated translation: `specification/<asset-name>/mcps/<api-spec-stem>/translation.json`
2. Extract the `tools` array from `translation.json` and write it as `specification/<asset-name>/mcps/<api-spec-stem>/.tool-list.json`. **This happens now, before Phase 4 pruning, so `.tool-list.json` captures the complete, unpruned tool set as the permanent backup:**
   ```bash
   jq '.tools' specification/<asset-name>/mcps/<api-spec-stem>/translation.json \
     > specification/<asset-name>/mcps/<api-spec-stem>/.tool-list.json
   ```

Both files must exist before proceeding. If either step produces an error → STOP and report the details to the user.

> **Do not regenerate `.tool-list.json` after this point.** Phase 4 prunes `translation.json`; if you re-ran `jq '.tools' translation.json > .tool-list.json` after pruning you would overwrite the full backup with the pruned set and lose the ability to re-add tools. `.tool-list.json` is written exactly once, here.

### Phase 4: Tool Relevance Pruning

The generator emits **every** tool the API exposes. A large SAP OData/REST API can produce dozens to hundreds of tools. Shipping all of them bloats the MCP server, inflates the agent's model context, and degrades tool-selection accuracy, even when the asset only needs to read a single entity. This phase trims `translation.json` down to the tools the asset actually needs.

Prune **`translation.json` only**. **Never** modify `.tool-list.json` (the full backup written in Phase 3 Step 3).

#### Step 1 — Determine the capability scope

Establish *what the asset is allowed to do*, in this priority order:

1. **Scope hint from the `specification` skill**: the per-asset spec `specification/<asset-name>/specification.md` carries an explicit capability-scope block written by the `specification` skill, e.g.:
   ```
   MCP API: sap.s4:apiResource:CE_COSTCENTER_0001:v1
   MCP tool scope: read-only
   Resources in scope: CostCenter, CostCenterText
   ```
   If present, this is authoritative. Use it directly. (`Resources in scope` names entity sets for OData or resource paths/tags for OpenAPI, match it against the appropriate tool metadata in Step 2.)
2. **Derived from the asset's task list**: if no explicit scope block exists, read the task list in `specification/<asset-name>/specification.md` and derive:
   - **Operation scope**: `read-only` if every task only lists/reads/queries/retrieves data; `read-write` if any task creates, updates, deletes, or triggers a side-effecting action.
   - **Resource scope**: the set of resources the tasks name (OData entity sets, or OpenAPI resource paths/tags).
3. **Ask the user**: if the tasks are too ambiguous to determine operation scope, ask: "Should this integration be read-only, or does it also need to create/update/delete data?" Do **not** guess.

Log the decision: `[MCP-SKILL] Scope: <read-only|read-write>; resources: <list>; source: <source>`.

#### Step 2 — Classify each tool

Read tool names, descriptions, and operation metadata from `translation.json` (never the raw API spec: it is too large for context). For each tool in `tools[]`, use the structured metadata, not guesswork:

- **Operation kind**: `odataType.<kind>.crudOperation` (`read` vs a write operation) and `openApiType.method` (`GET`/`HEAD` = read; `POST`/`PUT`/`PATCH`/`DELETE` = write). OData function/action imports and OpenAPI non-GET methods are writes/side-effecting.
- **Resource/subject**: the entity set or operation name in `odataType` (OData) / the path + `operationId` in `openApiType` (OpenAPI), matched against the in-scope resources.

**Always keep infrastructure tools (highest priority, checked first).** Some tools are not business capabilities at all; they are service-level infrastructure the agent needs to operate the API, and no user will ever ask for them by name. **Always classify these as `keep`, regardless of operation scope, resource scope, or name.** The identification is **structural and per API type**, never name-based (the name can change between generations). Handle each API type explicitly, they are different, do not apply one type's rule to the other:

> **Where to read the API type:** `target.type` is a top-level field **inside `translation.json`** (next to `mcpTranslationVersion` and `tools`), set by the generator in Phase 3. Read it from there with `jq -r '.target.type' translation.json`.

- **OData (`target.type` = `edmx`)**: an OData tool's `odataType` has exactly one of four shapes: `entitySet`, `operation`, `metadataRequest`, or `batchRequest`. The infrastructure tools are the ones with **neither `entitySet` nor `operation`**, i.e. `odataType.metadataRequest` (schema discovery, almost always named `get_metadata_*`) and `odataType.batchRequest` (transport-level `$batch` batching). **Metadata tools are mandatory for OData: without the metadata tool the MCP server is effectively unusable, because the agent cannot discover the schema it needs to build any request.** Keep them unconditionally. The `get_metadata_*` naming is only corroboration; the authoritative signal is the structural `metadataRequest`/`batchRequest` shape (if a future generation renames them, the structure still identifies them).
- **OpenAPI (`target.type` = `openapi-v2` / `openapi-v3`)**: OpenAPI has **no** infrastructure-tool concept. Every OpenAPI tool is bound to a concrete operation (`openApiType.path` + `method`, or `operationId`); there is no metadata/batch/discovery equivalent. So there is **no always-keep infrastructure floor for OpenAPI**, do **not** invent one, and do **not** apply the OData `metadataRequest`/`batchRequest` rule here. Prune OpenAPI tools purely on operation kind and resource scope.

For OData, these infrastructure tools do **not** count toward the resource scope and are never dropped by a `read-only` scope (metadata/discovery is read-only by nature; `$batch` is a transport wrapper, not an independent write).

Then classify every remaining tool as:

- **keep**: operation kind is within the operation scope **and** the tool's resource/subject is in the resource scope (or the resource scope is unspecified and the tool clearly serves the stated tasks).
- **drop**: operation kind is outside the operation scope (e.g. scope is `read-only` and the tool writes), **or** the tool clearly serves an unrelated resource/subject.
- **uncertain**: anything you cannot confidently place in `keep` or `drop` from the metadata and descriptions.

**Dependency hint (soft, nudges toward keep):** if a tool you are keeping references another tool by name in its description (e.g. "call `get_metadata_...` first"), that referenced tool is likely a genuine dependency. Treat the referenced tool as **`uncertain`** (so fail-open keeps it) rather than `drop` — **unless** keeping it would contradict the scope (e.g. the referenced tool writes and the scope is `read-only`), in which case the scope wins and you still drop it. Do **not** promote a referenced tool straight to `keep` on the strength of a description mention alone; a mention is a hint, not proof, and descriptions sometimes name write tools purely for context.

#### Step 3 — Apply pruning (fail open)

Remove **only** the `drop` tools from `translation.json`'s `tools[]`. Then apply these guardrails, in order:

1. **Fail open on uncertainty**: **keep** every `uncertain` tool. Never silently drop a tool you are not confident about. A missing tool is a silent runtime failure (the agent cannot perform an action it needed); an extra read tool is only mild bloat. The asymmetry is deliberate.
2. **Floor, always keep OData infrastructure tools**: for an OData translation (`target.type` = `edmx`), never drop a `metadataRequest` or `batchRequest` tool (identified structurally in Step 2). The agent cannot operate an OData service without the metadata/schema-discovery tool, so it is required even for the smallest read-only asset. (This floor does not apply to OpenAPI, which has no infrastructure tools.)
3. **Floor, never below the named tools**: never drop a tool that a spec task names explicitly.
4. **Floor, never zero**: pruning must never produce an empty `tools[]`. If your classification would remove everything, you have misread the scope: stop pruning, keep the full set, and ask the user which tools are needed. (A zero-tool translation deploys "green" but yields an agent with no capabilities, a known failure mode.)
5. **Surface the result for review**: after pruning, report to the user how many tools the API exposed, how many were kept, how many were dropped (and why), and how many were kept despite being uncertain. Keep this message free of internal file names (`.tool-list.json` is hidden and users cannot act on it; naming it looks like a bug). If any `uncertain` tools were kept, tell the user they can adjust the selection by: (a) using the UI, (b) editing the translation directly if they know what they are doing, or (c) simply asking the agent in natural language to add or remove specific tools. **For the agent (not the user):** re-adding a dropped tool means copying its full object from `.tool-list.json` back into `translation.json` (see "Re-adding tools later" below); the agent performs this on the user's behalf, the user does not touch the backup themselves.
6. **Pruning is best-effort, never a gate**: there is **no deterministic "too many tools" limit** — the real ceiling depends on the agent's model, which is unknown here. Keeping a large set (even if you pruned little or nothing) is acceptable; **always continue**, never block or fail because the kept count is high. When the kept count is large (e.g. in the hundreds), add a note to the user that a high tool count may cause runtime failures depending on the agent's model, and that they should contact their system administrator if they hit issues. The only hard requirement is that this pruning step *ran*; how much it removed is not a success criterion.

**You MUST apply the pruning with the mandatory `jq` command below (do not hand-edit `translation.json` by eye, and do not substitute a filter that only matches your keep-list by name).** The command is **the** enforcement of the always-keep-infra floor: it keeps your `keep` + `uncertain` names **and**, for OData, structurally re-admits every infrastructure tool even if you forgot to list it or its name changed. Pick the form that matches `target.type` in `translation.json`. The two forms are different on purpose; do not mix them.

Build `$keep` from your `keep` + `uncertain` classifications (business tool names).

**OData (`target.type` = `edmx`)** — keeps the named tools **plus** every `metadataRequest`/`batchRequest` tool (any `odataType` with neither `entitySet` nor `operation`), name-independently:
```bash
jq --argjson keep '["list_costcenters","read_costcenter"]' \
  '.tools |= map(select(
      (.name as $n | $keep | index($n))
      or (.odataType != null and (.odataType | (has("entitySet") or has("operation")) | not))
   ))' \
  specification/<asset-name>/mcps/<api-spec-stem>/translation.json > /tmp/translation.pruned.json \
  && mv /tmp/translation.pruned.json specification/<asset-name>/mcps/<api-spec-stem>/translation.json
```

**OpenAPI (`target.type` = `openapi-v2` / `openapi-v3`)** — there are no infrastructure tools, so keep strictly the named tools (no structural re-admit clause):
```bash
jq --argjson keep '["get_pet_by_id","find_pets_by_status"]' \
  '.tools |= map(select(.name as $n | $keep | index($n)))' \
  specification/<asset-name>/mcps/<api-spec-stem>/translation.json > /tmp/translation.pruned.json \
  && mv /tmp/translation.pruned.json specification/<asset-name>/mcps/<api-spec-stem>/translation.json
```

(`jq` cannot safely read and overwrite the same file in one step: the shell truncates it before `jq` reads. Always write to a temp file and `mv` on success, as above, so a failed filter leaves the original intact.)

Log the outcome: `[MCP-SKILL] Pruned: kept <k>/<total> tools (<u> kept as uncertain), dropped <d>; translation.json only; .tool-list.json unchanged`.

#### Re-adding tools later

To re-enable a tool that was pruned, copy that tool's full entry from the `.tool-list.json` array back into `translation.json`'s `tools[]`.

- `.tool-list.json` stores the complete, unpruned `tools` array only (full tool entries, not just names).
- It does **not** contain the rest of the translation document (`mcpTranslationVersion`, `target`, `serverInfo`, etc.).
- Therefore you may copy individual tool objects from it, but you must **never** try to rebuild a full `translation.json` from it.

Because `.tool-list.json` is never pruned, every tool the API exposes is always recoverable from it without regenerating.

### Phase 5: Post-Checks and Cleanup

Verify all the following conditions before reporting success:

1. For each API spec processed, **the following files exist**:
   - `specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<extension>` (the original API spec file copied in Phase 3 Step 2)
   - `specification/<asset-name>/mcps/<api-spec-stem>/translation.json`
   - `specification/<asset-name>/mcps/<api-spec-stem>/.tool-list.json`
2. `translation.json` has a non-empty `tools[]` array (pruning must never empty it).
3. `.tool-list.json` has **at least as many** tools as `translation.json` (it is the full backup; it must be a superset). Verify:
   ```bash
   test "$(jq '.tools | length' translation.json)" -le "$(jq 'length' .tool-list.json)"
   ```
4. **`translation.json` must never be missing while `.tool-list.json` is present.** If you ever observe this, treat it as a **corrupted asset** and **STOP**. Do **not** attempt to reconstruct `translation.json` from `.tool-list.json`: the backup contains only the `tools` array, not the rest of the translation (`mcpTranslationVersion`, `target`, `serverInfo`, etc.), so any reconstruction would be structurally invalid. Never try to recover from partial artifacts. The **only** valid recovery is to regenerate the whole asset from scratch via the normal flow (re-download the API spec and re-run `mcp_builder_generate_translation`, i.e. the **Overwrite** path in Phase 1); neither the agent nor the user should hand-build or patch `translation.json`. Any message shown to the user must stay generic and must not name internal files (e.g. "This MCP server asset is incomplete and needs to be regenerated.").
5. **OData infrastructure tools survived pruning (deterministic, mandatory).** For an OData translation (`target.type` = `edmx`), every `metadataRequest`/`batchRequest` tool in the full backup `.tool-list.json` **MUST** still be present in the pruned `translation.json`. This catches the case where pruning wrongly removed the metadata tool (which renders the MCP server unusable). Run this check; it must output nothing:
   ```bash
   # Lists any infra tool (neither entitySet nor operation) that exists in the backup
   # but is missing from the pruned translation. Any output here is a FAILURE.
   comm -23 \
     <(jq -r '.[] | select(.odataType != null and (.odataType | (has("entitySet") or has("operation")) | not)) | .name' .tool-list.json | sort -u) \
     <(jq -r '.tools[] | select(.odataType != null and (.odataType | (has("entitySet") or has("operation")) | not)) | .name' translation.json | sort -u)
   ```
   If this prints any tool name, pruning dropped a required infrastructure tool. Re-add it by copying its full entry from `.tool-list.json` back into `translation.json`'s `tools[]` (or re-run the mandatory Phase 4 Step 3 `jq`, which re-admits infra structurally), then re-run this check until it is empty. Do **not** report success while it prints anything. (For OpenAPI translations this check does not apply, there are no infrastructure tools; skip it.)
6. **`target.type` matches the spec's actual version.** **NEVER load the spec into context** — do not `cat`, `Read`, open, or otherwise print the spec file; a spec can be a single multi-megabyte line (common for EDMX) and will corrupt the context. Run **exactly** these two commands, which print only the version marker and the declared type:
   ```bash
   head -c 512 specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<extension> | grep -o -m1 -iE 'swagger"?[: ]+"?[0-9.]+|openapi"?[: ]+"?[0-9.]+|edmx:Edmx'
   jq -r '.target.type' specification/<asset-name>/mcps/<api-spec-stem>/translation.json
   ```
   Map the marker to the expected type: `swagger ... 2.0` → `openapi-v2`; `openapi ... 3.*` → `openapi-v3`; `edmx:Edmx` → `edmx`. If `target.type` does not match, change `target.type` in `translation.json` to the correct value.

If all conditions hold → Report success to the user with the file paths and the pruning summary from Phase 4 Step 3.
If any file is missing or any condition fails → STOP with an explanation of what failed.
If any file not mentioned above exists in the output folder → STOP with an explanation that the output contains unexpected files and list them.

### Phase 6: Sync to assets/ (existing solutions only)

**Skip this phase if `solution.yaml` does not exist** — initial creation; `setup-solution` will handle the copy from the main spec.

`specification/` is the source of truth — Phases 1–5 always leave `specification/<asset-name>/mcps/<api-spec-stem>/` populated before this phase runs. Phase 6 copies from there into `assets/` so the deployment picks up the changes.

If `solution.yaml` exists, check for a matching MCP server asset:

```bash
find ./assets -type d -name "mcp-translation"
```

For each found `assets/<mcp-server-name>/mcp-translation/`, compare `target.ordId` to the newly generated translation:

```bash
jq -r '.target.ordId' assets/<mcp-server-name>/mcp-translation/translation.json
jq -r '.target.ordId' specification/<asset-name>/mcps/<api-spec-stem>/translation.json
```

**ORD ID matches → update existing MCP server.** Copy the three files from `specification/` into the matched `assets/` folder (do not touch `asset.yaml` or the consuming agent — both are already correct):

```bash
cp specification/<asset-name>/mcps/<api-spec-stem>/translation.json  assets/<mcp-server-name>/mcp-translation/translation.json
cp specification/<asset-name>/mcps/<api-spec-stem>/.tool-list.json    assets/<mcp-server-name>/mcp-translation/.tool-list.json
cp specification/<asset-name>/mcps/<api-spec-stem>/api-spec.<ext>     assets/<mcp-server-name>/mcp-translation/api-spec.<ext>
```

**No ORD ID match → brand-new MCP server.** Do NOT create any files inside `specification/`. Execute **step 5** of `skills/setup-solution/SKILL.md` — `specification/<asset-name>/mcps/<api-spec-stem>/` is already populated (Phases 1–5 just ran), so step 5 will always find the files and copy them into the correct `assets/` structure, write `asset.yaml`, register in `solution.yaml`, and wire the consuming agent's `requires` entry.

## Related Skills
- `specification`: The `specification` skill detects API integrations during spec generation. When an integration is needed, it fetches the API specs and places them in `specification/<asset-name>/api-specs/`. The ORD ID and API type are determined from the files in this directory. It also writes the **MCP tool scope** block (read-only vs read-write + in-scope resources) into the per-asset `specification.md`, which Phase 4 of this skill consumes to prune the tool set.
- `agent` / `agent-extension`: wire the agent's tools from the **pruned** `translation.json` (`tools[].name`). They do **not** read `.tool-list.json` for wiring; that file is the full backup, so wiring from it would re-introduce every tool and defeat pruning.
- `mcp-mock-config`: generates `mcp-mock.json` from `translation.json`. **Whenever `translation.json` is modified** (tools added, removed, or changed), `mcp-mock-config` must be re-run to keep `mcp-mock.json` in sync. An out-of-sync mock file causes test failures or misleading mock responses.

## Troubleshooting

### Missing `specification/<asset-name>` directory or `specification/<asset-name>/specification.md` file/ Failed revalidation in Phase 1
Reinvoke `specification` skill to generate the specification folders and files first.

### No tasks referencing an API integration (keywords:"API", "integration", "OData", "REST", "service", or an ORD ID pattern like `sap.*:apiResource:*`).
STOP. This skill only applies to solutions that integrate with an API. If this skill was called from another skill, return the execution to the original caller, and explain this to the user (this skill might have been invoked unnecessarily but that doesn't impact the process negatively).

### No directory with `specification/<asset-name>/api-specs/`
If tasks refer an API integration(s) but no api specs folder was created, reinvoke the `specification` skill and ensure the API discovery step completes successfully. Context: This skill was likely invoked by an agent, which means that the agent may need to adjust its prompts or retry the discovery process, otherwise this skill wouldn't be called. 

### The agent kept many tools (little or nothing pruned)
There is **no deterministic "too many tools" threshold** — the real limit depends on the model the agent runs on, which is unknown at design time. So a large tool count is **not an error and must never block the process**. What matters is that pruning actually *ran* (Phase 4), not how much it removed. If pruning ran but kept most or all tools (e.g. the scope is genuinely read-write across many entities, or classification was mostly `uncertain` and fail-open kept them), that is acceptable: **continue**. When the kept count is large (e.g. in the hundreds), inform the user that a high tool count may lead to runtime failures depending on the agent's model, and that if they run into issues they should reach out to their system administrator. Only investigate as a real problem if pruning did **not run at all** or the downstream `agent` / `agent-extension` wiring read the wrong file: `agent` / `agent-extension` must wire from `translation.json`, not `.tool-list.json`. To re-run pruning against a corrected scope, use the **Update** path in Phase 1 (re-prunes without regenerating).

### The agent has zero / missing tools
Pruning dropped too much. This assumes `translation.json` **exists** and is structurally intact (only its `tools[]` is wrong); if `translation.json` is missing entirely, that is a corrupted asset instead, see Phase 5 condition 4 (full regeneration only). When `translation.json` is present: its `tools[]` must never be empty, and must never omit a tool a spec task names. Recover by copying the needed tool objects from the full backup `.tool-list.json` into the existing `translation.json`'s `tools[]` (the **Update** path in Phase 1). Then re-check the Phase 5 floors. Never ship a translation with an empty `tools[]`: it deploys "green" but produces an agent with no capabilities.

### The MCP server is unusable / the metadata (`get_metadata_*`) tool is missing (OData)
Pruning wrongly dropped an OData infrastructure tool. The metadata tool is **mandatory** for OData: without it the agent cannot discover the schema and the whole MCP server is effectively unusable. This happens when the agent builds a name-only keep-list and omits the metadata/batch tools instead of running the **mandatory** structural `jq` from Phase 4 Step 3. Fixes:

- Always run the **mandatory** Phase 4 Step 3 `jq` for OData (`target.type` = `edmx`). It re-admits every `metadataRequest`/`batchRequest` tool structurally (any `odataType` with neither `entitySet` nor `operation`), independent of the tool's name, so the metadata tool survives even if you never listed it.
- Confirm with the **Phase 5 condition 5** check (it must print nothing). If it prints a tool name, that infra tool was dropped; re-add it from `.tool-list.json` or re-run the structural `jq`, then re-check.
- Never identify infra tools by name (`get_metadata_*` is corroboration only). A future generation may rename them; the structural `metadataRequest`/`batchRequest` shape is the authoritative signal.
- This floor is **OData-only**. OpenAPI has no infrastructure tools, so do not look for or fabricate one there.

### `.tool-list.json` was accidentally pruned / is smaller than `translation.json`
`.tool-list.json` must be a superset of `translation.json`'s tools (it is the full, never-pruned backup). If it is smaller, it was wrongly overwritten after pruning. **Do not hand-rebuild either file from the other** — the backup lacks the full translation structure and `translation.json` has been pruned, so neither can reconstruct the other. The only correct fix is to regenerate the whole asset from scratch via the **Overwrite** path (re-download the API spec and re-run Phase 3, producing a fresh full `translation.json`, then re-derive `.tool-list.json` before Phase 4 re-prunes `translation.json`).

### Output Folder Naming Convention

The output subdirectory under `mcps/` is named after the API spec filename with the extension stripped. This creates a direct, deterministic link between each API spec and its generated MCP artifacts.

| API spec file                 | Output folder (`<api-spec-stem>`) |
| ----------------------------- | --------------------------------- |
| `supplier-invoice-cloud.json` | `supplier-invoice-cloud`          |
| `dispute-service.edmx`        | `dispute-service`                 |
| `business-partner-api.json`   | `business-partner-api`            |

This convention is used in Phase 1 (to check for existing files) and Phase 3 (to write output files).
