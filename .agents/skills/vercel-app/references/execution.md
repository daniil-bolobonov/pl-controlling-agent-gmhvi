# vercel-app: execution

Create production-quality frontend apps with Vercel v0 by composing a strong, structured prompt and then driving the gateway tools (`create_app`, `send_app_message`) — all pinned to `partner="v0"`.

This skill is the right tool when the user wants a *UI artifact*: a web app, dashboard, portal, landing page, internal tool, marketing page, or React/Next.js component. It is **not** for backend services, AI agents, n8n workflows, or CAP Apps.

## When to Use This Skill

**Both** conditions must be met:

1. The Vercel gateway tools (`create_app`, `send_app_message`) are available in the current environment.
2. The user **explicitly** asks to create an app with **Vercel** or **v0**.

Do **not** use this skill when:

- The user asks for a generic \"frontend app\", \"web app\", \"dashboard\", etc. without mentioning Vercel or v0 → use the `intent-analysis` → `product-requirements-document` → `specification` chain instead. (When the user *does* mention v0 or Vercel, this skill still runs `intent-analysis`, `product-requirements-document`, and `specification` first — see Step 1.)
- The user wants an **AI agent** → use `sap-agent-bootstrap` / `create-agent-extension`.
- The user wants a **workflow / automation** → use `n8n-workflow`.
- The user wants a **CAP App / Fiori app** → use the `intent-analysis` → `product-requirements-document` → `specification` chain.
- The user wants **simple static files or scripts** → use the file tools directly.

> Only `partner="v0"` is supported by this skill.

## Prerequisites

- The host agent (e.g. webagent) must expose the **gateway tools**: `create_app`, `send_app_message`. These ship with `@sap/webagent`'s `gatewayToolModule`. If they are not registered, stop and tell the user the host environment does not support v0 generation.
- The user has accepted that the app will be generated by an external provider (Vercel v0). The chat-completion worker synchronizes generated files by writing them directly to the current solution tree.

## Tools

For gateway calls, always pass `partner="v0"`. Do not ask the user which partner to use — this skill is v0-only.

### Gateway tools

| Tool | When to call | Notes |
|------|--------------|-------|
| `create_app` | Once per asset, **after** `intent-analysis`, `product-requirements-document`, and `specification` have run, to scaffold the initial app. | Required: `partner="v0"`, `prompt`, **`asset_path`** (the `assets/<asset-name>` directory `setup-solution` scaffolded), **`prd_files`** (**required** — see the "Attaching the specification with `prd_files`" section below). Optional: `project_name`, `solution_id`. On success, the webagent project context is switched to the new v0 project. |
| `send_app_message` | For every follow-up change the user requests. | Required: `partner="v0"`, `solution_id`, **`asset_path`**, `message`. The chat-completion worker synchronizes the resulting files by writing them directly to the solution tree. |

### Workspace inspection

| Tool | When to call | Notes |
|------|--------------|-------|
| `list_files` | Inspect generated source after the chat-completion worker has synchronized it. | Required: `path` set to the asset directory (for example, `assets/<asset-name>`). Lists the persisted solution tree; it does not call v0 or trigger synchronization. |

Do **not** use `write_file` / `update_file` / `execute_command` to hand-edit a v0-generated app. v0 owns the source of truth — round-trip changes through `send_app_message` so the provider stays in sync. The only exception is small post-processing (e.g. patching a config the user explicitly asked for that v0 cannot do).

### Choosing the right tool: `create_app` vs `send_app_message`

Always check the current solution's generation context and synced asset files before creating an app:

- **Asset already has a v0 app** (existing v0-synced files or a previously accepted generation request for this asset) → use `send_app_message` with the same `asset_path`, after persisted completion. Do **not** call `create_app` again for that asset — it would attach a *second* v0 project to the same asset.
- **Asset has no v0 app yet** → use `create_app` with that asset's `asset_path`.

Missing files alone do not prove the app is absent; generation may still be pending. If the existing generation context is unclear, clarify it with the user rather than creating another app.

Use `send_app_message` for the user's first follow-up request and subsequent changes after persisted completion. `create_app` already starts generation with the specification attached through `prd_files`.

A single solution can host **multiple** v0 apps as long as each lives under a distinct `assets/<asset-name>/` directory. The natural key for every gateway call is `(solution_id, asset_path)` — the same shape every other artifact uses (cap-app, n8n-workflow, mcp-server, …).

### `solution_id` parameter — what to pass

For `send_app_message`: **always pass the solution id of the active project** alongside `asset_path`. The pair forms the natural key for the partner mapping; either alone is ambiguous.

For `list_files`, pass the asset directory as `path` (for example, `assets/<asset-name>`). It reads files synchronized into the current solution and takes neither `partner` nor `solution_id`.

For `create_app`:

Default behaviour: **omit `solution_id`**. The host (`@sap/webagent`) auto-fills it from the current project context, so the new v0 app attaches to the solution the user is already working in. This is what you want 99% of the time.

Pass `solution_id` explicitly only when:

- The user has explicitly asked you to scaffold a v0 app for a *different* solution they own (rare).
- You are running outside any project context (very rare — most agent invocations are inside a project).

Never invent or guess a UUID. If unsure, omit the parameter and let the host default kick in.

### Attaching the specification with `prd_files` (REQUIRED)

`create_app`'s `prompt` is forwarded to v0's `description` field, which v0 caps at **1000 characters**. A real user request — once stack, screens, data, and design constraints are spelled out — will almost always overflow that limit. To keep `prompt` short while still giving v0 full context, this skill **requires** the `prd_files` parameter on every `create_app` call.

The specification is produced as part of Step 1 (`intent-analysis` → `product-requirements-document` → `specification`).
When calling `create_app`, always attach `specification/<asset-name>/specification.md` via `prd_files`.
If `specification/<asset-name>/api-specs/` contains API spec files, attach those in `prd_files` too so v0 can generate UI against real entity shapes.

Keep `prompt` short and directive — v0 treats the attached files as the source of truth. See Step 2 for how to compose the directive.

Pass `prd_files` as an array of paths relative to the solution version. Always include the specification. If any API spec files exist under `specification/<asset-name>/api-specs/` (`.edmx`, `.xml`, `.json`, `.yaml`), include those paths too — they help v0 produce more accurate mock data by providing the real entity shapes:

```
create_app({
  partner: "v0",
  prompt: "Build the application described in the attached specification.",
  asset_path: "assets/<asset-name>",
  prd_files: [
    "specification/<asset-name>/specification.md",
    // include any files found under specification/<asset-name>/api-specs/
    // e.g. "specification/<asset-name>/api-specs/metadata.edmx"
  ],
})
```

Do **not** call `create_app` without `prd_files`. If you find yourself wanting to, go back and run Step 1 first.

## Workflow

### **MANDATORY: Setup the Solution**

Before calling `create_app`, run the `setup-solution` skill to scaffold `solution.yaml` and `assets/<asset-name>/asset.yaml`. The v0 app must live as a `vercel-app` asset inside the solution so that Joule Studio runtime's deployer can pick it up — Joule Studio runtime's deployer supports `vercel-app` natively.

The final `assets/<asset-name>/asset.yaml` MUST conform to the canonical `vercel-app` schema at [`../assets/vercel-app.json`](../assets/vercel-app.json).
For convenience, a copyable YAML example derived from that schema is provided in the **asset.yaml** section of [`../assets/guidelines-vercel-app.md`](../assets/guidelines-vercel-app.md).
Copy the example verbatim and replace only the placeholders (`<asset-name>`); do not hand-write the file from memory or derive its shape from naming conventions.

Hard rules — these are the exact mistakes that break artifact recognition, so do not deviate:

- **`type` MUST be exactly `vercel-app`.** It is NOT `vercel-v0`, `v0`, or `frontend`. Any other value makes the backend fail to recognize the asset (the Solution Overview shows "no artifacts").
- **Use the `apiVersion` / `kind` / `metadata` / `container` structure from the template.** Do NOT write a flat `name:`/`type:`/`description:`/`label:` file — those top-level keys are not part of the schema.
- **`container.buildPath: .`** — v0-synced files land at the root of the asset directory (`assets/<asset-name>/app/...`, `assets/<asset-name>/package.json`, …). The deployer reads from the asset directory root.
- **`container.port: 5000`** — the port the v0 Next.js app listens on. Do not change unless the user has a hard requirement.

In `solution.yaml`, reference the asset with a **`ref`** entry (NOT `path`/`name`):

```yaml
assets:
  - ref: ./assets/<asset-name>/asset.yaml
```

If `setup-solution` produces a different shape (e.g. a flat file, `type: vercel-v0`, `buildPath: src`, or a `path:` entry in `solution.yaml`), correct it to match the template and the `ref` form above before proceeding.

### API spec decision rule

Determining which APIs an asset needs (and running discovery for them) is the `specification` skill's job, not this skill's. This rule only verifies that the artifacts the specification claims are actually present before handing off to v0:

- If the `specification.md` references API specs but `specification/<asset-name>/api-specs/` is empty or missing, tell the user v0 will fall back to generic mock data and require them to choose:
  1. Upload the missing spec file(s), or
  2. Explicitly confirm they want to proceed without them.
- Otherwise (the spec references no APIs, or the referenced spec files are present), continue.

Do not call `create_app` until the user has made that choice.

### Step 1: Ensure a PRD and a spec exist (MANDATORY before generating)

The v0 app must be built from a specification — not from the raw user prompt — to keep the generated app grounded in a real spec and to keep the prompt below v0's 1000-character limit. The `specification/<asset-name>/specification.md` (derived from `product-requirements-document.md`) is what v0 reads via `prd_files`; this step guarantees both the PRD and the spec exist before generating, but producing the intent and PRD is not this skill's job.

1. **Ensure the PRD exists.**
   - If `product-requirements-document.md` is present, continue.
   - Otherwise, invoke the `product-requirements-document` skill and continue from there. That skill owns the upstream chain: it will run `intent-analysis` first if `intent.md` is missing, and it handles all clarifying questions itself. Do not substitute your own clarifying questions for it.
2. **Ensure the spec exists — run the `specification` skill (Section A — Writing Specifications only).**
   - **Restriction (v0-specific):** run Section A only. Do **not** execute Section B (code generation), even in fast-track mode — only `vercel-app` drives what runs from Step 2 onwards.
   - **API spec check:** apply the _API spec decision rule_ defined above.
   - Next step: return here and continue to Step 2 of `vercel-app`.

Why this is mandatory:

- Real user requests almost always overflow v0's prompt cap once stack, screens, and data are spelled out. Attaching the specification via `prd_files` keeps the prompt itself small while giving v0 full context (see "Attaching the specification with `prd_files`").
- A user message like "build me a reading-list tracker" is too sparse for v0 to produce a useful first scaffold. The intent → PRD → spec chain extracts the structure v0 needs.
- Without the specification attached via `prd_files`, `create_app` will fail with `PROMPT_TOO_LONG` for any non-trivial request.

Do **not**:

- Skip to `create_app` even if the user says "just build it", "fast track", or provides what seems like a complete description. Fast-track mode applies to the IBD skills themselves (they will produce a leaner PRD); it does **not** bypass them.
- Gather product requirements yourself — that is the PRD/`intent-analysis` chain's job.
- Build the v0 prompt from the raw user message without going through the PRD.
- Allow the `specification` skill to auto-execute Section B — only `vercel-app` drives what runs next from Step 2 onwards.

After this step completes, the working directory should contain:

- `intent.md`
- `product-requirements-document.md`
- `specification/<asset-name>/specification.md`
- Any additional specification artifacts, such as downloaded API specs under `specification/<asset-name>/api-specs/`

Step 3 attaches the specification via `prd_files`.

### Step 2: Compose the v0 directive prompt

The specification from Step 1 carries the detail (purpose, users, screens, data, design). The `prompt` field on `create_app` is now a short **directive** that tells v0 to read the specification — not a duplicate of its content. Let v0 choose the stack based on what the specification describes; only pin a stack in the prompt when the specification does not specify one and the user has a hard requirement.

Default directive (suitable for most v0 apps):

```
Build the application described in the attached specification. Pick a clean, minimal
design tone unless the specification overrides it.
```

Use only when the user or specification has a hard stack requirement that the specification itself does not already convey:

```
Build the application described in the attached specification using <stack>.
<one extra sentence with non-default libraries or design overrides if needed>.
```

Keep the directive short — typically 1–3 sentences, well within v0's prompt cap. Do **not** restate purpose, users, screens, or data here; v0 reads those from `specification/<asset-name>/specification.md`.

### Step 3: Create the app

Call `create_app` exactly once. Pass `asset_path` — the directory `setup-solution`
scaffolded for this v0 app (e.g. `assets/sales-dashboard-app`) — and attach the
specification produced by Step 1 via `prd_files`. `prd_files` is **required** — follow the
same file inclusion rules described in the "Attaching the specification with `prd_files`" section above:

```
create_app(
  partner="v0",
  prompt=<the short directive from Step 2>,
  asset_path="assets/<asset-name>",
  prd_files=[
    "specification/<asset-name>/specification.md",
    // + any files under specification/<asset-name>/api-specs/
  ],
  project_name=<optional, e.g. "sales-dashboard-app">
)
```

After the call:

- The result identifies the requested `(solution_id, asset_path)`. Generation runs in the background.
- The chat-completion worker fetches, validates, and saves generated files to the solution tree for workspace inspection.
- Report that generation is running in the background and end the turn. Resume changes for this asset when the user returns and the current generation's files are confirmed saved. Preview availability is separate from that confirmation.
- Compatible hosts display **“Generation finished. Your app files have been saved.”** This is a session-local completion notice; delivery is not guaranteed.

### Step 4: Iterate with send_app_message

Every follow-up change the user explicitly requests goes through `send_app_message` after persisted completion (see "Choosing the right tool" above). Pass `asset_path` and `solution_id` (= the same key you used for `create_app`) on every call:

```
send_app_message(
  partner="v0",
  solution_id=<the solution>,
  asset_path="assets/<asset-name>",
  message=<change>,
)
```

Keep each message to a single, concrete change (one component, one screen, one refactor). Every message must stay within v0's per-message limit; if a request would exceed it, split it before sending — see the "Per-message size limit" subsection below.

Examples of typical follow-ups:

- "Add a dark mode toggle in the top right"
- "Replace the bar chart with a line chart and add a 30-day moving average"
- "The pricing table needs a 4th tier called Enterprise with a 'Contact us' button"

Guidance for follow-ups:

- **Functional / structural changes** (new components, new data, new behavior, layout changes) → use `send_app_message`. v0 will edit files and the chat-completion worker will synchronize them by writing them to the solution tree.
- **Pure visual tweaks** (colors, spacing, font size) → still go through `send_app_message`, but tell the user that for fine-grained design work the v0 web UI's Design Mode is faster than prompting.
- **One change per message** when the user gives a list — it lets v0 stay focused and produces cleaner diffs. Batch only when changes are tightly coupled.
- After acceptance, report background generation and end the turn as in Step 3.
- When the user resumes after confirmed persistence, inspect the current generation's synced files with workspace tools such as `list_files` if verification is needed.

#### Per-message size limit — split large changes incrementally

v0 caps a single chat message at **~1000 characters**. The gateway enforces
this and returns a typed error code when a message is too large:

```
PROMPT_TOO_LONG: message length 1842 exceeds v0 per-message limit 1000.
Split the change into smaller incremental messages.
```

When you receive `PROMPT_TOO_LONG` (or anticipate it), do **not** retry the
same prompt. Instead:

1. **Decompose** the user's request into the smallest set of independent
   changes that, applied in order, achieve the same end state. One feature,
   widget, screen, or refactor per message.
2. **Confirm the plan** with the user in one short message before starting:
   list the steps you intend to send and ask for a yes/no go-ahead.
3. **Send one step at a time** with `send_app_message`. Report acceptance and end the turn. Continue the agreed plan when the user resumes after that step's files are confirmed saved.
   - If a step fails, stop and surface the error to the user.
4. **Summarize the confirmed saved changes** when the user resumes after the final step.

Example decomposition (long request → 4 incremental sends):

> User: "Replace the dashboard with: 4 KPI cards (MRR, churn, NPS, new
> users), a 30-day revenue line chart with moving average, a recent-orders
> table with filters, dark mode toggle, and brand color emerald."

```
1. Add the 4 KPI cards (MRR, churn, NPS, new users) above the existing chart.
2. Replace the bar chart with a 30-day revenue line chart with a moving-average overlay.
3. Add a recent-orders table with date/status filters under the chart.
4. Add a dark-mode toggle in the top-right header and switch the brand accent to emerald.
```

Each step should fit comfortably under the 1000-char limit on its own.

## Specification Quality Checklist

The specification attached via `prd_files` is what drives v0. Before calling `create_app`, confirm the `specification/<asset-name>/specification.md` produced by Step 1 satisfies each check:

- [ ] **Actionable build tasks** — project-specific tasks are concrete `- [ ]` items grouped under `##` headers, with one or more per functional requirement (not a vague summary)?
- [ ] **Business rules as tasks** — each business rule is captured as a specific TODO?
- [ ] **Discovered API specs referenced** — any APIs found during discovery are listed by name / ORD ID with paths to the downloaded files under `specification/<asset-name>/api-specs/`, so v0 can build UI against real entity shapes?

If the specification does not cover one of these, rerun the `specification` skill to generate them again. Do not patch the gap by stuffing detail into the `create_app` prompt.

## Guardrails

### Communication
- Be direct. Complete all mandatory Step 1 skills before building — no extra clarification round beyond what those skills already handle.
- Always echo back your understanding (1–3 lines) before calling `create_app`.
- Follow Step 3's background-generation response.

### Scope
- Pin `partner="v0"` everywhere.
- Do not hand-edit v0-generated files with `write_file` / `update_file` unless the user explicitly asks for a one-off patch v0 cannot do.
- Do not use this skill for backend services, agents, n8n workflows, or CAP Apps — route to the appropriate skill.
- Do not invent authentication, payments, or database integrations. v0 is UI-first; flag these as out-of-scope and suggest a follow-up integration step.

### Safety
- Don't paste secrets, API keys, or customer PII into a v0 prompt. v0 sends prompts to an external provider.
- If the user asks for something that requires real backend wiring (auth, DB, payments), call it out before generating and offer a placeholder/mock instead.

## Examples

### Example 1: Vague request → intent → PRD → build

**User:** "Build me a frontend app with v0 for tracking my reading list."

1. Run the mandatory chain (see "Setup the Solution" + Step 1): `setup-solution` (scaffolds `assets/reading-list-app/asset.yaml` with `type: vercel-app`) → `intent-analysis` → `product-requirements-document` → `specification` (Section A only, writes `specification/reading-list-app/specification.md`).
2. Call `create_app` with a short directive and the specification attached:
   ```
   create_app(
     partner="v0",
     prompt="Build the application described in the attached specification.",
     asset_path="assets/reading-list-app",
     prd_files=["specification/reading-list-app/specification.md"],
     project_name="reading-list-app",
   )
   ```
   No API spec files exist for this app, so only the specification is passed.
3. Report background generation and end the turn as in Step 3.

### Example 2: Detailed request — still goes through intent → PRD

**User:** "Build a Next.js + Tailwind + shadcn landing page for a SaaS called Pulse with v0: hero with email signup, 3-tier pricing table, FAQ accordion, footer. Brand color emerald. No placeholder copy — write real marketing copy aimed at engineering managers."

The user already gave a lot of detail, but the IBD chain still runs — it normalizes the request into the specification format v0 reads from and keeps the prompt under the 1000-character limit.

1. Run the mandatory chain for `assets/pulse-landing` (see "Setup the Solution" + Step 1): `setup-solution` → `intent-analysis` (fast-track is fine here — the user was specific, so its clarifying questions stay minimal) → `product-requirements-document` → `specification` (Section A only).
2. Call `create_app` with the specification attached and a short directive. Include API spec files from `specification/pulse-landing/api-specs/` if any exist (see "Attaching the specification with `prd_files`" above):
   ```
   create_app(
     partner="v0",
     prompt="Scaffold a Next.js (App Router) + Tailwind + shadcn/ui landing page from the attached specification. Use emerald as the brand accent.",
     asset_path="assets/pulse-landing",
     prd_files=["specification/pulse-landing/specification.md"],
     project_name="pulse-landing",
   )
   ```
3. Report background generation and end the turn as in Step 3.

### Example 3: Follow-up iteration

**User (after the landing page is up):** "Add a customer logos strip below the hero, and change the pricing CTA on the top tier to 'Start free trial'."

1. Call `send_app_message` with the existing app's natural key:
   ```
   send_app_message(
     partner="v0",
     solution_id=<the active solution>,
     asset_path="assets/<asset-name>",
     message="Add a customer logos strip below the hero (6 placeholder logos in a responsive grid). Change the pricing CTA on the top tier from its current text to 'Start free trial'.",
   )
   ```
2. Report background generation and end the turn as in Step 3.
